execution authorizationc back to ToC or Class ToC

IRI: https://w3id.org/pionera/daimo#ExecutionAuthorization

A governed authorisation resource (a prov:Entity) that links exactly one accepted odrl:Agreement (daimo:derivedFromAgreement) to the it6:Run invocations it permits. Deliberately NOT a subclass of odrl:Agreement: the agreement is the negotiated policy artefact that carries the ODRL permissions, whereas the authorization is the derived resource that ties that agreement to concrete executions, a grantee, and an expiry. Keeping them apart lets one agreement back several authorizations and prevents the authorization from being (mis)typed as an odrl:Policy. SHACL invariant INV-9 checks that the grantee (daimo:grantedTo) is the odrl:assignee of the agreement it derives from.
A governance artefact that binds an accepted odrl:Agreement (via daimo:derivedFromAgreement) to the concrete MLDCAT-AP run invocations it authorises (daimo:authorizesRun), for a specific grantee agent (daimo:grantedTo) and until an expiry timestamp (daimo:expiresAt). The authorization is NOT the agreement itself: it is a separate individual that operationalises a single agreement over one or more executions.
Is defined by
https://w3id.org/pionera/daimo
Example 
After a successful DSP contract negotiation the accepted terms are represented as an odrl:Agreement; a distinct ExecutionAuthorization then declares daimo:derivedFromAgreement that agreement, grants execution to the consumer (daimo:grantedTo), covers one or more runs via daimo:authorizesRun, and expires at a daimo:expiresAt timestamp.

Entity c

shared evaluation contextc back to ToC or Class ToC

IRI: https://w3id.org/pionera/daimo#SharedEvaluationContext

A reified grouping of the conditions under which model results are comparable: task, dataset, dataset version, protocol and, when applicable, random seed. Does not claim that those facets alone guarantee comparability (the same metric and compatible conditions are also required), nor that every facet of a study is covered (split strategy, hyperparameters, metric formula). Absence of a seed is not an assertion of complete reproducibility; it records that the declared procedure does not use one. This is the minimum grouping required by CQ-V1..CQ-V3.
A reified grouping of the conditions under which model evaluations are comparable: task, dataset, dataset version, evaluation protocol and, when applicable, random seed.
Is defined by
https://w3id.org/pionera/daimo
Example 
Two candidate models evaluated on the same SharedEvaluationContext (identical it6:Task, dcat:Dataset, daimo:datasetVersion, daimo:protocol, and — when the procedure is stochastic — the same daimo:randomSeed) can be ranked on the same metric; changing task, dataset, version or protocol, or comparing under incompatible metrics, breaks comparability. A deterministic protocol such as leave-one-out may omit the seed.

derived from agreementop back to ToC or Object Property ToC

IRI: https://w3id.org/pionera/daimo#derivedFromAgreement

Links a daimo:ExecutionAuthorization to the single accepted odrl:Agreement whose terms it enforces over concrete runs. Functional: each authorization derives from exactly one agreement (a run's authorisation must trace to one accepted set of terms). Asymmetric: the authorization and the agreement are distinct individuals. Deliberately NOT declared a subproperty of prov:wasDerivedFrom: prov:wasDerivedFrom has domain and range prov:Entity and expresses generic data-lineage between entities; using it would (i) force every odrl:Agreement to be a prov:Entity, and (ii) blur the specific governance meaning 'the accepted ODRL agreement this authorization enforces'. No property in ODRL, DCAT, MLDCAT-AP, PROV-O or DSP carries this exact meaning, so daimo:derivedFromAgreement is a native, unaligned object property; see alignment.ttl for the non-alignment rationale.
The accepted odrl:Agreement that a given execution authorization operationalises.

https://w3id.org/pionera/daimo

The ExecutionAuthorization granting flood-risk-v2 execution to Leganés declares daimo:derivedFromAgreement the odrl:Agreement produced by the UPM–Leganés contract negotiation, so the concrete run authorisation is traceable back to the exact accepted terms.

has domain
execution authorization c

for serviceop back to ToC or Object Property ToC

IRI: https://w3id.org/pionera/daimo#forService

Links an I/O contract to the specific dcat:DataService endpoint it applies to. Functional: each contract describes exactly one service (several contracts may still describe the same service if a real need arises, e.g. distinct authentication variants, but a single contract targets one service). Asymmetric: a contract and the service it describes are distinct individuals. Introduced to remove the ambiguity that appears when a ModelDeployment exposes several services (daimo:exposedAs) and declares several contracts (daimo:hasIOContract) with no per-endpoint link, which otherwise forces CQ-R4/CQ-D3/CQ-E1/CQ-G2 into a cartesian join between services and contracts. No external property (e.g. dcat:endpointDescription) carries this exact meaning; see alignment.ttl for the non-alignment rationale.
The DCAT data service (deployment endpoint) that a given I/O contract describes.
Is defined by
https://w3id.org/pionera/daimo
Example 
On a deployment exposing a REST endpoint and a gRPC endpoint, the REST IOContract (application/json, oauth2-bearer) declares daimo:forService the REST dcat:DataService and the gRPC IOContract (application/x-protobuf, mtls) declares daimo:forService the gRPC dcat:DataService, so each endpoint's format and authentication method are unambiguous.

has characteristics: functional, asymmetric

has domain
I/O contract c
has range
Data Service c

granted toop back to ToC or Object Property ToC

IRI: https://w3id.org/pionera/daimo#grantedTo

Links an execution authorization to the grantee agent it authorises. Functional: one grantee per authorization. Deliberately NOT declared rdfs:subPropertyOf odrl:assignee: odrl:assignee has domain odrl:Policy, so — now that daimo:ExecutionAuthorization is no longer an odrl:Agreement/odrl:Policy — that alignment would re-type every authorization as an odrl:Policy and reintroduce the very conflation DAIMO-ISSUE-02 removes. The intended equivalence (the authorization's grantee IS the odrl:assignee of the agreement it derives from) is instead enforced by SHACL invariant INV-9 rather than by OWL subsumption. Also deliberately NOT aligned to prov:qualifiedAssociation, whose range is a reified prov:Association object, not the agent itself.

has characteristics: functional

has domain
execution authorization c
has range
Agent c

random seeddp back to ToC or Data Property ToC

IRI: https://w3id.org/pionera/daimo#randomSeed

Fixes stochastic components of the evaluation procedure when that procedure uses them. Functional: a given SharedEvaluationContext must not declare two incompatible seeds. Optional: SHACL allows cardinality 0..1 because applicability depends on the evaluation procedure, not on a universal DAIMO list of 'stochastic protocols'. Omitting the seed is not a claim of complete reproducibility; it only records that the declared protocol does not use a seed.
Integer seed that fixes the stochastic components of an evaluation protocol when that protocol uses them.
Is defined by
https://w3id.org/pionera/daimo
Example 
A holdout or k-fold protocol that shuffles folds records daimo:randomSeed 42; a fully deterministic leave-one-out protocol omits the property.
